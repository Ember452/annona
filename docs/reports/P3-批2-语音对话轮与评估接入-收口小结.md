## 2. 五个真雷（本机证据 + CI 两轮红）

1. **VOICE 报告撞外键**（数据模型级）。`interview_report.session_id` / `interview_evaluation.session_id`
   在 V13 都是 `REFERENCES interview_session(id)`，而语音会话的宿主是 `voice_session`（V18），
   同一列不能有第二个父表 → 语音收口事件一到，`reportRepository.save(...)` 当场违反 FK。
   修法 = V21 解除两处外键（`interview_report.user_id` 的级联**保留**），证伪点钉进
   `EvaluationFlowIT.voiceReportIsPolymorphicOnRealDb` 与 `MigrationShapeIT.voiceTurnAndPolymorphicReportShape`。
   代价登记为 TD-16（`interview_evaluation` 无 `user_id`，账号硬删需应用层按会话删）与
   TD-17（planner 靠 `JOIN interview_session`，语音报告不反哺 plan）。
2. **TTS 发射器自锁**。`submit()` 在调用线程 `acquireUninterruptibly()`，而排空线程（常驻
   `wait(100)`）与合成任务都跑同一个 `aiIoExecutor`：单线程池或池被占满时，合成任务永远排
   在排空线程后面 → `submit` 永不返回。`mvnw -B verify` **不是变红，是整条构建挂死**（4 分钟
   无输出后手工杀进程）。修法 = 许可在异步任务内部取，池满时退化为"超时跳句"；发射器类注
   写明"池必须至少能同时跑 1 排空 + N 合成"，单测执行器改 4 线程池。
3. **降级路径其实没降级**。`doSpeakTurn` 在 try 之外 `ttsProvider.orElseThrow()`：TTS 装配为
   `none` 时整轮抛异常 → 字幕也不发；且 handler 的 `speaking` 闸门只在 `onText` 里释放，
   于是此后每次"回答完毕"都被"面试官发言中"拒死，会话不可恢复。同类问题还有 ai-io 池
   `AbortPolicy` 拒绝 `speakTurn` 时的静默吞轮。修法 = 发射器可选、`finish()` 挪进 finally、
   `deliver()` 用 `AtomicBoolean` 守"恰好一次 text"、拒绝分支同步降级；
   `VoiceInterviewServiceTest` 5 例分别钉 TTS 缺席 / LLM 缺席 / `streamChat` 抛出 / 空输出 / 池饱和。

另外修了两条**从未跑过的测试期待**（不是"改用例让它变绿"，是用例与自身输入/新签名矛盾）：
`SentenceSplitterTest.splitsAcrossDeltas` 的输入 `feed("第一句的前半")` + `feed("半。第二句。")`
拼接后是"前半半。"，期望值却写"前半。"——改输入不改语义；`VoiceSessionServiceTest.transitionsDelegate`
仍按旧签名断言 `finalizeSession`，而新版先做归属校验 → 改钉"不属该用户直接 false 且不发事件"。

4. **上下文装配直接崩（CI run #115 唯一红点）**。`VoiceProperties` 只注册在
   `VoiceWebSocketConfig` 上，而那个配置带 `@ConditionalOnWebApplication(SERVLET)`；
   `VoiceInterviewService` 与 handler 却是不受那道门控的普通 bean，在
   `webEnvironment=NONE`（docker IT 的主流形态）里照样被创建。主类没有
   `@ConfigurationPropertiesScan`，于是配置被跳过 = bean 缺席 = 整个 ApplicationContext 起不来，
   **断言一行没跑到，61 个 IT 连坐报错**。修：注册点移到 `VoiceInterviewService`
   （`SkillQueryService` 先例），门控配置只留端点接线。§3 已配机检。

   这一条是本机拿不到的凭证：雷 1/2/3 靠 `mvnw verify` 与单测当场暴露，雷 4 只能由
   docker IT 暴露——正是 dockerless 开发模式已知的那类反馈延迟（风险表"本机无 Docker 导致
   反馈延迟变大"）。机检已补成反射型 slice 测试，把它拉回本机可验。

5. **手打答案不再进 transcript（run #116 唯一红点）**。批 2 重写 `handleSubmit` 时把
   `sessions.appendTranscript(...)` 这一句弄丢了：键入文字只进内存答案缓冲与结构化的
   `voice_message` 轮次，`voice_session.transcript` 却不再累加。而 V18 定的是
   **"音频不落库，转写是唯一存留物"**：一个完全降级到手动输入的会话会留下空转写。
   批 1 的 `VoiceFlowIT.voiceFullFlow` 正是用这条断言拦住的（改前的 diff 已核：
   `git diff 29696aa HEAD` 里那行 `appendTranscript` 在 handleSubmit 中消失）。
   修：补回该行——结构轮次与转写聚合是同一句话的两个视图，不是二选一（`c1d21c3`）。
   同次提交还把该 IT 的回声窗 sleep 重新锚定：开场白之后现在紧跟一个面试官轮，
   只等开场白的窗会被后到的 chunk 吃掉上行——**没削弱任何断言**，拦住这个回归的那条原样保留。

## 4. 协议与两端一致性

批 2 未新增帧类型，只扩了两处语义，改协议两端同批落地：

- 下行 `audio_chunk`：一轮可有多块，`data=""` + `isLast=true` 是排空末块标记（不播、不延长回声窗）。
- 上行 `control`：新增 `submit`（回答完毕，语音作答收本轮）与 `audio_done`（播放队列排空，
  服务端 `EchoGate.reset()` 立即解禁，时间窗退为无信号兜底）。
  前端 `AudioChunkQueue` 是 `audio_done` 的唯一生产者——没有它，`EchoGate.reset()` 就是死代码。

## 5. 客户端播放为什么必须串行

`useVoiceSession` 原来对每个 `audio_chunk` 直接 `new Audio().play()`。批 1 一轮只有一块，看不出
问题；批 2 一轮 N 句，同时播会把句子叠成一团噪音。改为队列串行（播完一段取下一段），且
`playClip` 的注入契约写明"播完/被拦截/解码失败都必须回调 onEnded"——否则一轮卡死后续全部
句子。被自动播放策略拦截时：标记 `playbackBlocked` 交 UI 引导手势，本段放弃但队列继续推进。
