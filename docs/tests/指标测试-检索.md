# 指标测试 · 检索（P1a-07 / P1a-09）

> 定位：这份文档既是**指标口径的定义**，也是**你要跑真数字的教程**。
> P1a 出口条件③要的是"混合检索相对纯向量的 Recall@K 提升有实测数字"，
> 而数字只有你自己（或带 Key 的 CI）跑出来的那次才算——CI 默认没有 embedding Key，
> 那一轮是**管道回归**，不是质量结论。

## 1. 指标定义与口径

| 指标 | 口径 | 为什么这么定 |
|---|---|---|
| **Recall@K** | 前 K 条命中里，标注相关文档被找回的比例，按 query 求平均（同一文档多个块只算命中一次） | K=3 对齐产品实际喂给 LLM 的条数（RRF 后 TopK=4，去冗余留 3） |
| **MRR@K** | 第一条相关命中名次的倒数，未命中记 0，按 query 求平均 | 只看"找没找到"会掩盖排序质量；问答层只吃头部几条，位次就是质量 |
| **P50 / P95** | `POST /api/retrieval/query` 返回的 `tookMs`（**含**查询向量化 + 两条通道 SQL + 融合） | 端到端口径才对用户有意义；分开测会漏掉 embedding 的网络耗时 |
| **分桶** | 每条 query 带 `bucket ∈ {symbol, phrase, clause}`，分桶各出一遍 Recall/MRR | 关键词通道的价值集中在 `symbol`（专有名词/编号）与 `clause`（条款编号）；不分桶就答不出"提升到底来自哪一路" |

三条必须守住的解释规则：

1. **`--embedding-provider` 必须如实传。** `fake` 的向量由文本哈希生成、与语义无关，那一轮
   `SEMANTIC` 的召回本质是随机数——脚本会在输出里显式打警告，报告与 `retrieval_eval_run`
   也都带这一列。**不同 provider 的两轮数字不可比较**（检索按 `kb_doc.embedding_model` 过滤，
   换 provider 后旧文档根本不会进候选集）。
2. **同批语料、同 `queries.json` 才是 A/B。** 三档（`BOTH`/`SEMANTIC`/`KEYWORD`）由同一个脚本
   一次跑完，共用一次上传，保证候选集完全相同。
3. **`retrieval_eval_run` 是投影，真相源是 JSON 报告。** 报告落在 `out/rag-eval/`（CI 走
   artifact），定稿数字必须誊写进 `docs/benchmarks/`，不能只留在表里。

## 2. 跑一轮真数字（三条路径，任选）

### 路径 A：本机 Docker（最快拿到可决策的数字）

```bash
# 1) .env 至少要有（Key 用你自己的 OpenAI 兼容 embedding 服务）
#    ANNONA_SECRET_KEY / SPRING_DATASOURCE_PASSWORD / S3_* 四项
#    S3_ENABLED=true
#    ANNONA_MODEL_EMBEDDING_PROVIDER=openai-compatible
#    ANNONA_EMBEDDING_BASE_URL=https://dashscope.aliyuncs.com/compatible-mode/v1
#    ANNONA_EMBEDDING_API_KEY=***
#    ANNONA_DEFAULT_EMBEDDING_MODEL=text-embedding-v3
#    ANNONA_EMBEDDING_DIMENSIONS=1024      # 必须是 1024，换维度=新迁移
docker compose --env-file .env -f docker/docker-compose.yml up -d --wait
docker compose -f docker/docker-compose.yml ps      # 5 个服务全 healthy（含 storage）

# 2) 跑评测（应用对外端口是 nginx 的 80，或直连 server 的 8080）
python3 scripts/rag-eval/eval.py --base-url http://localhost:8080 \
  --label "本机真模型-0928" --embedding-provider openai-compatible \
  --embedding-model text-embedding-v3
```

首次会打印 `main dict load finished`（jieba 词典加载，约 0.4s，一次性）。
脚本自己注册一个临时账号、上传 `scripts/rag-eval/corpus/` 全部讲义、等 READY、跑三档。

### 路径 B：部署环境

同一条命令，把 `--base-url` 换成已部署的栈地址即可。前提与路径 A 相同：该环境的
`ANNONA_MODEL_EMBEDDING_PROVIDER=openai-compatible` 且维度 1024，否则召回数字无意义。

### 路径 C：CI（无 Key 时只验管道）

配了仓库 Secret `EVAL_EMBEDDING_API_KEY` → eval job 自动用真模型出决策级数字；
没配 → 退回 `provider=fake`，只验"上传→READY→三档检索→报告落盘"整条链没断。
看结果：Actions 里 `RAG Eval` job 的 `rag-eval-report` artifact。

## 3. 对比两轮 / 多轮

```bash
python3 scripts/rag-eval/eval.py --compare out/rag-eval/eval-A.json out/rag-eval/eval-B.json
```

输出两张表：按 `mode` 的头部指标（列头带 provider 标注，避免把 fake 和真模型并排比较），
以及 `BOTH` 档的分桶 Recall。**先看 `symbol`/`clause` 两桶有没有提升**——那是关键词通道
存在的理由；如果只有 `phrase` 提升而两桶没动，说明收益全来自向量侧。

## 4. 常见失败与判读

| 现象 | 根因 | 处置 |
|---|---|---|
| `等待 READY 超时` | 消费者没开（`ANNONA_KNOWLEDGE_INGEST_ENABLED` 默认 false）或 S3 不可达 | compose 需显式开；查 `docker compose logs server` |
| 某篇 `入库失败：向量化模型未配置` | provider=none | 配 Key 或明确本轮只测关键词通道 |
| 所有文档瞬间 `FAILED`，原因含"维度" | 模型不是 1024 维 | 换 1024 维模型；换维度属于新迁移 |
| `SEMANTIC` 档全空、`KEYWORD` 有结果 | 语料的 `embedding_model` 与当前配置不一致（常见于换了模型或 fake/真模型来回切） | 对文档点"重建"；这不是检索坏了 |
| 老文档（V5 之前入库的）关键词搜不到 | `tokens` 为 NULL，生成列 `tsv` 为空 | 点文档行的"重建"（走解析→分块→向量化全链路，会补 tokens） |
| 两轮同参数数字差很多 | 其中一轮是 fake；或 corpus 变了 | 核对报告里的 `embedding_provider` 与 `corpus` 字段 |

## 5. 跑完之后必须落的三件事

1. 把 `BOTH` vs `SEMANTIC` 的 Recall@3 / MRR@3 与 P50/P95 誊进
   `docs/benchmarks/检索基线-YYYY-MM-DD.md`（**新建**，含日期、模型 id、语料清单、provider），
   并在 `docs/README.md` 登记。
2. 若 `BOTH` 不优于 `SEMANTIC`：按 `chinese-keyword-search-adr` 的重新评估分支处理，
   **先于批 3（P1a-08）的验收收口**——这是把 P1a-09 排在 P1a-08 前面的全部意义。
3. 若 `top4_miss_type`（脚本 `misses[]` 里的 `reason` + 人工看 `top_docs`）以"术语相近但
   语义不同"为主：那是 rerank 通道的证据，按 ADR "何时重新评估" 提 rerank ADR，
   不要直接加模型。

多轮对比（A/B 或回归）用 `scripts/rag-eval/compare.py`：喂 ≥2 份报告 JSON，输出
逐 mode 指标表 + 分桶表 + 命中差异明细；**不同 provider 的两轮不可比较**（脚本会显式警告）。

自动化对照：`RetrievalFlowIT`（CI，真实 PG + fake 向量）验三档的**形状**与可见性隔离，
本教程验**质量**。两者互不可替代。
