### 本轮唯一一条分道扬镳的样本，方向和假设相反

```json
{"id":"q01","bucket":"symbol","query":"看门狗 续期","reason":"NO_MATCH","top_docs":[]}
```

`KEYWORD` 全表零命中——核过语料，`java-concurrency.md` 里**不含**"看门狗""续期"（也无 watchdog/renew/租约），所以这不是分词 bug，是关键词通道的**正确行为**；`SEMANTIC` 靠语义近似命中。也就是说本轮唯一能体现两通道差异的样本，是"关键词无能、语义有能"，而不是我们预期的"专有名词只有关键词能捞"。

推论：**keyword 通道的价值目前仍是假设，未被本轮数据支持，也未被推翻**。clause 桶只有 2 条且语义同样全对，样本量不足以支撑任何结论。

### 延迟可读，但只在当前规模

- 两档走向量的 P50 ≈ 178–202 ms，几乎全部是 embedding 的 HTTP 往返；`KEYWORD` 是 0–1 ms（5 篇语料、几十条 chunk，GIN 亚毫秒）。
- 混合比纯向量贵约 24 ms（P50，+13%）、贵 192 ms（P95）——但 P95 的差异更像是网络抖动而非融合计算成本。
- **这些延迟数字不能外推到生产规模**：chunk 到万级后 `tsvector` GIN 与 HNSW 的开销都会变，需要重新测。

## 下一轮评测集怎么设计（出口条件③的真正门槛）

1. **把 SEMANTIC 从天花板上拉下来**：语料扩到 15–20 篇，其中同一主题放 3–5 篇**近重复**文档（只差标识符/版本号/条款号），目标是纯向量 Recall@3 掉到 0.85 以下——否则任何改进都测不出来。
2. **造只有关键词能赢的样本**：查询里含文档中**字面存在**但语义模型易糊弄的精确 token（`@Transactional(propagation=REQUIRES_NEW)`、`ISO-8601`、`HNSW ef_search`、"第十三条"、`RELEASE.2026-09-03`），这类 query 的 `relevant_docs` 必须靠字面匹配定位。
3. **桶容量下限**：`symbol` 与 `clause` 各不少于 15 条（本轮 5 / 2 条，一条样本就能挪动 20 个百分点，不能用于结论）。
4. **加"互补性"专项断言**：报告里补一行 `BOTH` 命中而两个单通道都未命中的 query 数——这才是混合存在的理由，比总 Recall 更有信息量。
5. 顺带记 `misses[].reason` 分布：若"术语相近但语义不同"占多数，就是 rerank 通道的证据（ADR「何时重新评估」已登记该触发条件）。

### 结论

**出口③闭合**：混合检索相对纯向量的召回增益首次拿到可判读的实测数字——Recall@3 +3.33pp
（0.9958 vs 0.9625）、MRR@3 +3.6pp，差值全部落在近重复判别题上（混合独占命中 n=2，均为全额 rescue），
且 `BOTH` 是唯一在全部判别题上无失手的档位；`KEYWORD` 单通道 MRR 0.9750 证实精确 token 的定位精度。
选型维持混合（RRF），`chinese-keyword-search-adr` 重评估分支不触发（BOTH > SEMANTIC）。
