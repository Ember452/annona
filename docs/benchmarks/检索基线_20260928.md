## 能读出来的 / 不能读出来的

**能读（且不依赖 provider）**

- **关键词通道在真库上真的能工作**：`KEYWORD` 一档不走向量，它检验的是 V5 的 `tokens → to_tsvector('simple', …) → tsv` 生成列 + `tsquery` 命中 + `ILIKE` 专有名词兜底这条链。0.95 / 0.90 说明分词入库与查询侧同词典、生成列可查、兜底谓词有效。
- **RRF 没被噪声拖垮**：`BOTH`(0.95) 追平较好的那一路，说明融合实现不会在语义通道质量差时把结果拉到低于单通道。这是形状验证，不是收益证明。
- **管道端到端可用**：注册→上传→解析→分块（写 `tokens`）→向量化→READY→三档检索→报告落盘→写投影表，全链在 CI 跑通。首轮曾因 Recall 计算未去重而算出 1.25，被服务端的 `[0,1]` 校验当场拒绝（`e323489` 修）。

**不能读**

- `SEMANTIC` 的 0.50 不是"纯向量方案的质量"，而是随机基线的形状（5 篇语料、K=3）。
- `BOTH − SEMANTIC = +45 个百分点` 这类写法**在本轮不成立**，因为差值全部来自 fake 噪声，不代表混合检索的真实增益。
- P50/P95（1–2 ms）**不含 embedding 的 HTTP 往返**：fake 不联网，而真模型下那才是检索延迟的主体。生产延迟必须重新测。

## 本轮顺带暴露并修掉的缺陷

关停日志把正常退出记成故障：`@PreDestroy` 用 `interrupt` 停消费线程，而 Redisson 抛的是包了一层的 `RedisException(InterruptedException)`，`CompletableFuture.get()` 抛出时会清掉中断标志，`while (!isInterrupted())` 便不再能停止循环——结果是关停时刷一条吓人的 `任务流消费异常 … 1000ms 后重试`，并且在上下文销毁期间还可能再取一条消息处理。已在 `RedissonTaskStream.runLoop` 按异常链判定中断、重新置位标志并安静退出，`RedissonTaskStreamInterruptTest` 钉住"包装层级变化也要能红"。
