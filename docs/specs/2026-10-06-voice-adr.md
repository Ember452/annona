# ADR: 语音链路——ASR/TTS 端口落 common、独立语音会话、JSON 协议与降级路径

- 日期 / 状态：2026-10-06 / Accepted（2026-10-10 增补修订 1，批 2 落地时定案）
- 相关：[P3_VOICE_PLAN](../plans/P3_VOICE_PLAN.md)、[qa-streaming-adr](2026-09-28-qa-streaming-adr.md)（StreamingChatProvider 先例）、[model-api-key-adr](2026-09-25-model-api-key-adr.md)（用途体系）、[llmprovider-metering-adr](2026-09-29-llmprovider-metering-adr.md)（scene/purpose 二维）

## 背景

P3 语音面试开工（P3-01..07）。借鉴地图 C 表点名 🅖 voiceinterview 全套为最直接借鉴源，但要求
"ASR/TTS 走 `ModelProvider` 抽象而非直连 DashScope"。现状：SPI 六端口无音频位；common 有
`StreamingChatProvider` 先例；V10 `llm_provider_config.purpose` 已含 `asr/tts` 位但零消费方；
运行时模型调用走 env 配置（BYOK 运行时解析是独立欠账，见技术债）。用户裁决：分三批、
DashScope 首实现、**独立语音会话**（不套用 interview_session）。

## 决策

1. **ASR/TTS 端口落 `annona-common`，不进 `annona-spi`**（AGENTS §4 端口判据：无第三方
   实现方需求；与 StreamingChatProvider 同先例——流式/会话语义不进对外契约 jar）：
   - `StreamingAsrProvider`：`start(options, callbacks)` 返回会话句柄（`sendAudio(byte[])` /
     `close()`），回调 `onReady/onPartial/onFinal/onError`（形状照 🅖 QwenAsrService）。
     服务端 VAD 断句；音频约定 PCM 16kHz 16bit 单声道。
   - `TtsProvider`：`byte[] synthesize(String text, TtsOptions options)` 句级一次性合成
     （🅖 QwenTtsService 同语义）；句子级并发调度是 voice 编排层职责，不是端口契约。
2. **实现只在 `annona-infrastructure`**：DashScope qwen3-asr/tts-flash-realtime 经
   JDK `java.net.http.WebSocket` 直连（不引 dashscope-sdk-java）；Fake 双实现供 CI/本机。
   装配按 ChatConfig 同款三态（`annona.model.asr/tts.provider` = none/fake/dashscope，
   默认 none），错误后移使用点、启动不拦。
3. **独立语音会话**（用户裁决）：V18 建 `voice_session`（状态机 CREATED→ACTIVE→PAUSED→
   FINALIZED/ABANDONED、direction、开场白与 ASR/TTS 配置快照、延迟指标列）。对话式面试：
   开场白可配置 + LLM 流式追问 + 多轮上下文；题库材料经 `QuestionQueryService` 只读消费
   （免白名单）。**音频不持久化，仅存转写文本**（设计 §隐私红线）。
4. **评估接入（批 2 落地，方向在此定）**：voice 交卷发布独立领域事件（不冒用
   `InterviewFinalizedEvent`——sessionId 宿主不同）；评估侧经 voice 暴露的共享只读接口
   装配会话内容，评分口径仍走 `QuestionQueryService.gradingByIds`，保证 P3-05
   "同题库得分可比"。
5. **WS 协议**：`/ws/voice`，JSON 文本帧 + base64 PCM（上行 `{type:'audio',data}` 与
   控制帧；下行 `subtitle/audio_chunk/text/control/error`，🅖 形态）。握手鉴权复用
   `IdentityProvider`（Cookie/platform/none 三模式同 SessionAuthFilter 口径）。
6. **计量**：ASR 记秒数、TTS 记字符数，借 `token_usage.prompt/completion_tokens` 列
   （purpose='asr'/'tts'，scene 增 'VOICE' 属 V11 CHECK 双处一致纪律）。**何时重新评估**：
   托管代持上线需按音频计费对账时，扩列迁移。
7. **降级路径**（P3 出口③）：TTS 不可用 → 文字面试（题干字幕仍下发）；ASR 不可用 →
   手动提交文字。LLM/ASR/TTS 任一通道未装配（none）时使用点报 `BusinessException`，
   错误码归 2600 语音段。

## 否决的备选

| 备选 | 否决原因 |
|---|---|
| 业务直连 DashScope（无端口抽象） | 借鉴地图"必须改什么"列明令禁止；换厂商（讯飞三元组）要重写业务层 |
| ASR/TTS 端口进 `annona-spi` | 无第三方实现方需求；会话/流式语义进对外契约 jar 后改一次是破坏性变更（StreamingChatProvider 先例） |
| 语音套用 interview_session（音频模态） | 用户裁决独立会话；套用需 voice→interview 写路径白名单且追问形态受 pack 约束 |
| 二进制 WS 帧 + JSON 控制帧（🅜 形态） | 省约 33% 体积但引入 pendingBinaryQueue 未就绪竞态处理；16k 单声道 200ms 块下 base64 开销可接受；有需要再切换（协议版本号预留） |
| 前端 MicVAD 客户端 VAD（🅖 引 CDN 依赖） | 设计口径是服务端 VAD 断句；省一个 CDN 脚本与 onnxruntime 依赖 |
| dashscope-sdk-java 引入 | SDK 带全量传递依赖；JDK HttpClient WebSocket 足以承载 Omni 协议；SDK 探不到的协议差异在手工冒烟校准，必要时 SDK 只进 infrastructure（端口契约不变） |

## 后果与约束

- voice 是 `modules/voice` 新顶层包（handler/session/asr/tts/audio/metrics/config/dto 子包
  按结构文档 §9）；跨模块只读消费 questionbank 的 `QuestionQueryService`（全仓免白名单先例类）。
- `annona-server` 需新增 `spring-boot-starter-websocket` 依赖（上行音频必须双向 WS）。
- 延迟埋点口径：端到端（停止说话→首包音频）是唯一对外验收数字；ASR 首字/LLM 首 token/
  TTS 首包只是链路段（设计 §10）。
- 真库行为（V18 形状、voice_session 状态机）由 docker IT 钉；DashScope 直连协议差异在
  手工冒烟校准，不进 CI。

## 何时重新评估

- 出现第二个 ASR/TTS 厂商接入（讯飞三元组凭据模型）且端口形状不够表达时；
- TTS 需要真流式（首包 <200ms 目标提级）时，`TtsProvider` 一次性语义扩为流式端口；
- 托管代持按音频量计费对账时，`token_usage` 扩时长/字符列；
- BYOK 运行时解析落地时，asr/tts 通道同批接入（现状 env 配置与 chat/embedding 同口径）。

## 修订 1（2026-10-10，批 2 落地时定案）：对话轮模型 + 报告归属多态化

原决策 3 只定了「独立语音会话」，决策 4 把「报告归属方案」显式留给装配时定案。
批 2 落地时两件事必须定形，本节是它们的契约源头（V19/V20/V21 与代码按本节实现）。

### 1. 题库驱动的对话轮（V19）

- `voice_session` 扩 `question_ids JSONB`（开场时从 `QuestionQueryService.activePool` 截取的
  题队列快照，保序）+ `current_question_seq`（作答轮落库后用条件 UPDATE 推进，仅 ACTIVE）。
- 新表 `voice_message`：`role IN ('QUESTION','ANSWER')`、`seq` 会话内唯一
  （`uq_voice_message_seq`）、`question_id` 可空引用 `qb_question`。QUESTION = 面试官发言
  （LLM 过渡语 + 题干），ANSWER = 候选人本轮作答。
- **题干保持原意**是 P3-05 可比性的口径保证：提示词只允许 LLM 加过渡语，不许改写问题；
  评分仍走 `QuestionQueryService.gradingByIds`，与文字面试同一 rubric。
- 队列为空（未绑方向或题库空）时会话退化为自由问答，**不进评分**（无 `question_id` 的
  ANSWER 轮被装配侧过滤掉）。
- 多轮上下文本期只做「按 `historyMaxTurns` 截最旧」；完整 `VoiceContextCompressor` 归批 3。

### 2. 报告归属：`interview_report` 多态化（V20 + V21）

语音报告**落同一张 `interview_report`**，用 `session_type` 区分宿主；代价是外键必须解除：

- V20：`interview_report` 加 `session_type`（`chk_report_session_type` = INTERVIEW/VOICE，
  DEFAULT INTERVIEW 使存量行零迁移）+ `(user_id, session_type)` 索引；`token_usage.scene` 增 `VOICE`。
- V21：`interview_report.session_id` 与 `interview_evaluation.session_id` 对 `interview_session`
  的外键**删除**（VOICE 行的 session_id 宿主是 `voice_session`，同列不能有两个父表）。
  `interview_evaluation` **不加 `session_type`**：它的所有读路径都经 session_id（报告装配按
  report 的类型分流，planner 复习题选取靠 JOIN interview_session 天然只认文字面试），
  没有任何消费方会读这个列——按简单优先不加。
- `interview_report.user_id` 的外键与级联**保留**——用户删除仍能级联清掉报告。

**否决的备选**：

| 备选 | 否决原因 |
|---|---|
| 语音另建 `voice_report` + `voice_evaluation` | 评估落库/报告页轮询/趋势与可比性判定全要按类型写两套，与「入口平级、内核共用」主张相悖，且是三个方案里工作量最大的 |
| 交卷时投影成 `interview_session` + `interview_answer` | 与决策 3「独立语音会话」的用户裁决相抵；且要造 `plan`/`total_count`/`direction_id NOT NULL` 的假数据，污染 interview 域 |

**已知的代价（诚实记账，不是可选项）**：

1. 两表失去 `session_id` 级联。`interview_evaluation` 没有 `user_id` 列，将来做账号硬删时必须
   应用层按会话删（或届时无 user_id 就删不掉）——登记技术债，触发时机 = 注销/数据导出落地时
   （[DATA_EXPORT_PLAN](../plans/DATA_EXPORT_PLAN.md)）。
2. `DecisionFlowIT` 的面试样本口径是 `interview_report JOIN interview_session`，**语音报告天然不计入
   planner 的面试样本**。这符合「planner 以面试侧数据为主输入」的现状，但意味着语音结果暂时
   不反哺 plan——要反哺是独立决策，届时改本条。
3. 依赖 `session_id` 外键做完整性兜底的测试夹具需改为显式清理（本批已改）。

### 3. 作答装配经共享只读端口

`shared/voice/VoiceEvalQueryService`（形状同 `InterviewEvalQueryService`，返回同一 `EvalAnswer`），
实现落 voice 模块，evaluation 经接口消费——跨模块只读免白名单（qa-streaming-adr §决策 7 先例）。
语音轮无追问槽位，`followUpIndex` 恒 0。归属校验：会话不属该用户返回空（不抛，防跨用户读）。

### 4. 收口事件与降级路径口径收紧

- voice 收口赢者发布 `VoiceSessionFinalizedEvent`（事务内发布，`AFTER_COMMIT` 消费），evaluation
  据此建 `sessionType=VOICE` 的 PENDING 报告并投递——**不冒用** `InterviewFinalizedEvent`。
- 决策 7 的降级路径在本批被写成可验证的行为约束（原表述只说了「TTS 不可用→文字」）：
  ① TTS 通道缺席或抛错时，面试官轮**必须仍下发 `text` 帧**（纯字幕），不得因装配缺席而让整轮
  静默；② LLM 通道缺席时直读题干/结束语；③ ASR 缺席或中断时切手动提交；④ **面试官轮无论怎么走
  异常分支，都必须释放 `speaking` 闸门**——否则候选人每次「回答完毕」都被「面试官发言中」拒死，
  会话不可恢复。①②③④各有单测钉（出口③的凭证）。

### 5. 装配约束（CI run #115 红过一次之后才写下的）

voice 的 bean 分属两类门控，不得推给同一份配置：

- `VoiceWebSocketConfig` 带 `@ConditionalOnWebApplication(SERVLET)`（`@EnableWebSocket` 的
  支撑设施依赖 servlet 语境）+ `annona.voice.enabled` 门控（无 DB 的 test profile 冒烟必须关）。
- `VoiceInterviewService` / `VoiceWebSocketHandler` / `VoiceSessionService` 是普通 `@Service`/`@Component`，
  **在任何上下文都被创建**，包括 `webEnvironment=NONE`（docker IT 的主流形态）。

因此 `VoiceProperties` 的注册点必须在不受 web 门控的一方（现注在 `VoiceInterviewService` 上，
`SkillQueryService` 先例），因为主类没有 `@ConfigurationPropertiesScan`：只挂在那份门控配置上，
NONE 上下文就缺这个 bean，整个 ApplicationContext 起不来（实际代价：61 个 docker IT 连坐，
断言一行没跑到）。本仓已配机检 `PropertiesRegistrationSiteTest`（纯反射、本机可跑）。
