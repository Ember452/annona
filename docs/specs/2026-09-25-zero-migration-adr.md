# ADR: annona 不做代码搬运，作为全新项目独立实现

- 日期：2026-09-25
- 状态：Accepted
- 相关：[../annona-项目设计文档.md](../annona-项目设计文档.md)

## 背景

手上三个仓库覆盖了目标能力的大部分：`interview-guide`（Spring Boot，面试引擎/知识库/语音/评估）、`MockPilot`（Spring Boot，混合检索/SingleFlight/熔断/线程池隔离）、`summer-checkin`（Next.js + Prisma，自习室/3D 岛/计划/智能体/记账）。

最初的方案是"选骨架仓库 + 移植"：以 interview-guide 为底座，把 summer-checkin 的 React 组件搬到 Vite、其服务端 CRUD 用 Java 重写，从 MockPilot 摘防护组件。

## 决策

**annona 作为全新项目从零编写，不做任何代码搬运。** 三个既有仓库只作为「能力清单」与「优秀设计」的参考源：功能表里用 `G/M/S/新` 标注借鉴来源，但所有代码按 annona 自身的设计重写。产品与功能设计层面不受"哪边能复用"约束。

## 否决的备选

| 备选 | 否决原因 |
|---|---|
| 以 interview-guide 为骨架 fork 改造 | 会继承其包名、配置约定、无状态鉴权等历史决策，annona 的闭环设计（方向主数据、决策留痕、质量分级）与它的既有模型冲突，改比分成本高 |
| Next.js 全栈为骨架（summer-checkin） | 废掉 Java 侧全部工程能力（评估引擎、语音链路、限流熔断），而这些是最难重建的部分 |
| 逐文件移植 + 改名 | 表面省时间，实际是把三个项目的架构分歧合并成一个：依赖版本、分层约定、异常体系都要各留一套，长期维护成本高于重写 |
| 保留 ES 做默认检索 | 四中间件破坏"clone 下来能跑"；文档量在上线初期撑不到 ES 的优势区间 |

## 后果与约束

1. 工期评估必须以"重写"为准，不能沿用"移植很快"的估计。缓解手段是分期（P0→P5）且每期有可截图产出物。
2. 借鉴上游代码片段时，AGPL-3.0 传染适用：凡实质性参考 `interview-guide` 的代码，必须保留同许可并在 README 致谢。因此 annona 自身也用 AGPL-3.0。
3. 不引入任何 `interview-guide` 的 Maven 依赖，避免版本锁死。
4. 参考实现随时可读，但**禁止"照抄后改名"**——设计文档里明确记录的机制（如 `StructuredOutputInvoker` 统一重试、`AbstractStreamProducer`）要以 annona 的命名与边界重新落地。

## 何时重新评估

- 若某能力的重写成本实测超过总工期 30%，且该能力与本项目设计无冲突（例如纯算法类的分块器），可单独引入依赖或复制代码，但必须在 `docs/specs/` 追加一条 ADR 并附许可处理说明。
